# Инструкция по промптингу

## Базовые принципы

1. Хороший промпт = **задача + контекст + ограничения + формат ответа**.
   Пропущенная часть — это то, что модель додумает за вас.
2. Одна задача за раз. Большую задачу режьте на итерации.
3. Результат всегда проверяется: `make check`, тесты, чтение кода глазами.
4. Пишите однозначно: одно предложение — одна мысль, условие перед командой
   (принципы STE, см. навык `asd-ste100-ru`).

## Фреймворки

Фреймворк — мнемоника, чтобы не забыть части промпта. Не культ: для простого
вопроса хватит одного предложения.

| Фреймворк | Расшифровка | Когда применять |
|-----------|-------------|-----------------|
| **RTF** | Role — Task — Format | Быстрые задачи: «сделай X в формате Y» |
| **RACE** | Role — Action — Context — Expectation | Рабочий универсал: код, анализ, ревью |
| **CARE** | Context — Action — Result — Example | Когда есть эталонный пример результата |
| **COSTAR** | Context — Objective — Style/Tone — Audience — Response | Универсальный дефолт; рекомендован вендорами (Qwen/Alibaba). Тексты и документация (README, спецификация) — целиком; код — редуцируется до RACE |
| **CREATE** | Character — Request — Examples — Adjustments — Type of output — Extras | Длинные задачи с кучей требований |

**Какой фреймворк выбрать.** Универсальный дефолт — **CO-STAR**: его
рекомендуют вендорские гайды (официальный гайд Qwen / Alibaba Cloud Model
Studio описывает ровно эти шесть элементов), он же победил на Singapore
GPT-4 Prompt Engineering Competition 2023. Для кодовых задач элементы
Style/Tone/Audience обычно схлопываются, и CO-STAR редуцируется до своего
подмножества **RACE**: Action — одна задача, Context — файлы и правила,
Expectation — проверяемый критерий («`make check` зелёный»). Практично так:
тексты и документацию (спецификация, README, письма) пишите по CO-STAR
целиком, кодовые задачи — по RACE. RTF — только для мелочей без контекста;
CARE — когда есть образец (few-shot); CREATE заменяйте цепочкой промптов.
И помните оговорку самого гайда Alibaba: не каждому промпту нужны все шесть
элементов — адаптируйте под задачу. С кодовым агентом контекст уже живёт в
репозитории (`AGENTS.md`, спецификация, ADR), поэтому боевой промпт
сокращается до «задача + критерий готовности»; полный фреймворк нужен там,
где контекста в репо ещё нет.

### Пример: RACE на этом ДЗ

> Ты — senior Go-разработчик, ревьюишь учебный код (**Role**).
> Добавь в REPL команду `remove-animal <вольер> <имя>` (**Action**).
> Проект: `internal/cli/cli.go` вызывает `internal/zoo`; правила — в `AGENTS.md`;
> ошибки сравниваем через `errors.Is` (**Context**).
> Готово, когда `make check` зелёный и есть table-driven тест на новую ветку
> ошибки (**Expectation**).

### Пример: COSTAR для спецификации

> Контекст: учебное консольное приложение «Зоопарк», Go 1.26.
> Задача: помоги заполнить раздел «Команды и сценарии» в `docs/spec.md`.
> Стиль: технический, короткие предложения.
> Аудитория: проверяющий-преподаватель.
> Формат ответа: markdown-таблица «Команда / Описание / Пример ввода / Пример
> вывода».

## Техники

- **Zero-shot** — запрос без примеров. Нормально для простых задач.
- **Few-shot** — 2–3 примера «вход → выход» в промпте. Сильнейший приём для
  нестандартных форматов: покажите один заполненный ADR — получите такой же.
- **Chain-of-Thought** — «рассуждай по шагам» для задач на логику и отладку.
  Для кодового агента аналог: «сначала план изменений, код — после моего ок».
- **Prompt chaining** — цепочка промптов вместо одного гигантского:
  спецификация → ADR → скелет → команда за командой. Совпадает с порядком
  работы в README.
- **Self-critique (рефлексия)** — «перечитай свой код и найди 3 проблемы»,
  «прогони мысленно тесты». Дёшево, ловит глупые ошибки.
- **Негативные ограничения** — явно запрещайте: «без внешних зависимостей»,
  «не меняй `go.mod`», «не трогай `master`».
- **Разделители** — код, ошибки и логи вставляйте в fenced-блоки (```),
  отделяя от текста задания.
- **Структурированный вывод** — просите формат: «таблицей», «diff», «списком
  файлов с изменениями». Свободный текст плохо проверяется.

## Работа с кодовым агентом: практика для этого ДЗ

1. **Контекст уже в репозитории** — `AGENTS.md`, `docs/spec.md`, ADR.
   Ссылайтесь на них («действуй по AGENTS.md»), не копируйте правила в каждый
   промпт.
2. **Ошибки — целиком.** Вставляйте полный вывод компилятора/линтера/тестов,
   а не пересказ «что-то не собралось».
3. **Маленькие итерации.** Одна команда/фича за запрос; после каждой зелёной
   итерации — коммит. Так откат бесплатный.
4. **Просите объяснить.** «Почему здесь `errors.Is`, а не `==`?» — ответы
   понадобятся на защите; код, который вы не можете объяснить, не ваш код.
5. **План до кода.** Для нетривиального: «предложи план, код не пиши» →
   обсудили → «реализуй шаг 1».
6. **Логируйте.** Каждое содержательное обращение — строка в `AI_USAGE.md`
   (что просили, что приняли, что переписали).

## Антипаттерны

| Антипаттерн | Чем заканчивается | Замена |
|---|---|---|
| «Сделай ДЗ целиком» | Код, который вы не понимаете; 0 на защите | План + итерации (см. выше) |
| «Сделай лучше» | Произвольные правки | Конкретный критерий: «покрой тестами Remove» |
| Пять задач в одном промпте | Половина потеряна | Один промпт — одна задача |
| Вставка кода без чтения | Линтер/CI красный, мусор в AI_USAGE | Читайте diff, прогоняйте `make check` |
| Пересказ ошибки своими словами | Агент лечит не то | Полный вывод в fenced-блоке |
| «Удоли и напиши заново» при мелкой правке | Потеря работающего кода | Точечная правка с контекстом |

## Чек-лист хорошего промпта

- [ ] Понятно, **что** сделать (одна задача)
- [ ] Дан **контекст**: файлы, версии, ссылки на AGENTS.md/спецификацию
- [ ] Перечислены **ограничения** и запреты
- [ ] Есть **критерий готовности** (тест, `make check`, формат)
- [ ] Указан **формат ответа**
- [ ] Для нестандартного формата — **пример** (few-shot)
