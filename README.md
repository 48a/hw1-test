# ВышКат — учёт прокатного парка

Консольное приложение на Go для приёмки транспорта и учёта вещей.
Оно показывает количество объектов, суточную энергию всего баланса,
технику для новичков и инвентарные номера.

Выдача в аренду, оплата и сотрудники не входят в приложение.
Данные хранятся в памяти и теряются после выхода.
Правила команд описаны в [спецификации](docs/spec.md).

## Запуск и проверки

Нужен Go 1.26 или новее. Рабочий код использует только стандартную библиотеку.
Для проверок нужен golangci-lint v2. Для генерации моков нужен mockery v3.
Мок уже находится в репозитории, поэтому для запуска тестов mockery не требуется.
Testify и его зависимости унаследованы от шаблона и используются только в тестах.

```bash
make run        # интерактивное меню
make demo       # готовый сценарий успешных действий и ошибок
make build      # бинарный файл bin/rental
make test       # юнит-тесты
make cover      # покрытие по функциям и общий итог
make test-race  # тесты с детектором гонок
make mocks      # перегенерация мока техосмотра
make check      # форматирование, vet, линтеры, тесты
make help       # все команды
```

## Работа с меню

Введите номер команды. Затем вводите каждое запрошенное поле на отдельной строке.
Название может содержать пробелы. Дробную часть расхода отделяйте точкой.

| Команда | Действие |
|---------|----------|
| `1` | Добавить транспорт после техосмотра |
| `2` | Добавить вещь |
| `3` | Показать количество транспорта, вещей и общую суточную энергию |
| `4` | Показать принятый транспорт с простотой от 6 |
| `5` | Показать названия и инвентарные номера всего баланса |
| `0` | Завершить программу |

Команда `1` спрашивает вид: `1` — электросамокат, `2` — велосипед,
`3` — электровелосипед. Затем идут название, номер, простота от 1 до 10
и состояние: `1` — исправен, `2` — неисправен.
Для электротранспорта дополнительно вводится суточный расход энергии.
Настоящий сервис техосмотра принимает только исправный транспорт.

Команда `2` спрашивает вид: `1` — шлем, `2` — док-станция без зарядки,
`3` — зарядный шкаф. Затем идут название и номер.
Расход энергии вводится только для зарядного шкафа. Вещи не проходят техосмотр.

Название обязательно. Номер — положительное десятичное число, общее для всего
баланса. Номера `001` и `1` считаются одинаковыми. Расход не может быть
отрицательным, бесконечным или `NaN`.

При ошибке программа объясняет причину и предлагает повторить команду.
Отказ техосмотра не добавляет объект и не занимает номер.
Конец ввода завершает программу, не сохраняя незавершённое добавление.

### Короткий пример

Введите последовательно:

```text
1
1
City Pro
101
6
1
1.5
2
1
Шлем
201
3
4
5
0
```

Основные строки ответа:

```text
Принято: City Pro [101]
Принято: Шлем [201]
Транспорт: 1; вещи: 1; всего: 2; Суточная энергия всего баланса: 1.50 кВт·ч
Техника для новичков (простота >= 6):
- City Pro [101], простота: 6
Весь инвентарь:
- City Pro [101]
- Шлем [201]
До свидания!
```

### Полная демонстрация

`make demo` читает [docs/demo.txt](docs/demo.txt). Сценарий показывает пустые
списки, приёмку всех шести видов объектов, отказ техосмотра, повторные номера,
неизвестные команды и виды, ошибки полей, отчёт и обе подборки.
Прерывание ввода и ошибки потоков отдельно проверяют тесты консоли.

Итог демонстрации: 3 транспорта, 3 вещи, 6 объектов, 6.75 кВт·ч в сутки.
В подборку новичкам входят City Pro с простотой 6 и электровелосипед с простотой 10.
Велосипед с простотой 5 остаётся в общем инвентаре.

## Структура и решения

```text
cmd/rental/          сборка зависимостей и запуск
internal/domain/     транспорт, вещи, техосмотр, парк, отчёт
internal/cli/        чтение полей и вывод результатов
docs/spec.md         спецификация
docs/adr/            три действующих решения и история шаблона
docs/demo.txt        ввод для демонстрации
AI_USAGE.md          журнал использования ИИ
```

Основные типы находятся в [internal/domain](internal/domain):

- [Inventory](internal/domain/asset.go) задаёт название и инвентарный номер.
- [EnergyConsumer](internal/domain/energy.go) задаёт суточное потребление энергии.
- [Transport](internal/domain/transport.go) добавляет простоту и исправность.
- `Scooter`, `Bicycle`, `ElectricBicycle` представляют виды транспорта.
- [Helmet, DockStation, ChargingCabinet](internal/domain/items.go) представляют вещи.
- [Park](internal/domain/park.go) принимает объекты и строит отчёты.
- [ServiceCenter и BasicServiceCenter](internal/domain/service.go) отвечают за решение техосмотра.

Общие данные собраны в закрытых структурах `asset`, `vehicle` и `energy`.
Конкретные типы встраивают нужные структуры. Это композиция Go:
она заменяет наследование классов и не создаёт пустых методов.
Например, велосипед и шлем вообще не реализуют `EnergyConsumer`.
Поля закрыты, конструкторы проверяют значения. Методов изменения после приёмки нет.

Парк хранит один список объектов в порядке добавления. Для отчёта он проверяет
интерфейсы `Transport` и `EnergyConsumer`, поэтому зарядный шкаф тоже входит
в расход всего баланса. Списки возвращаются копиями.
Ошибки объявлены в [errors.go](internal/domain/errors.go) и сравниваются через `errors.Is`.

Действующие ADR написаны до реализации:

1. [ADR-0003: модель через композицию](docs/adr/0003-domain-model.md).
2. [ADR-0004: пошаговое меню и память](docs/adr/0004-console-and-storage.md).
3. [ADR-0005: техосмотр через DI](docs/adr/0005-service-center.md).

ADR-0001 и ADR-0002 сохранены как история шаблона и помечены заменёнными.
Путь модуля `example.com/zoo` сохранён, чтобы не менять `go.mod` без отдельного запроса.

## Как применён SOLID

| Принцип | Где применён и зачем |
|---------|---------------------|
| SRP — одна ответственность | `cli` отвечает за диалог, конструкторы — за допустимые значения, `Park` — за баланс, `BasicServiceCenter` — за решение техосмотра. Изменение текста меню не меняет домен. |
| OCP — расширение без изменения общей логики | `Park.Report` и `Park.Beginners` работают через интерфейсы. Новый транспорт не требует правок этих методов. |
| LSP — взаимозаменяемость | Все три вида транспорта подходят для `AddTransport` и техосмотра. Общие контракты одинаковы: номер, простота 1–10, исправность. Велосипед не обязан притворяться потребителем энергии. |
| ISP — небольшие интерфейсы | `Inventory`, `EnergyConsumer` и `ServiceCenter` содержат только нужные операции. Шлему не нужны методы энергии или простоты. |
| DIP — зависимость от абстракции | `Park` зависит от `ServiceCenter`. Настоящую реализацию выбирает `cmd/rental`, а тест передаёт мок. |

Наиболее явно применён **DIP**: решение техосмотра можно заменить, не меняя парк.
DI — передача зависимости снаружи — реализована аргументом `NewPark(service)`.
Контейнер зависимостей для одного сервиса не нужен.

Сознательно ограничен **OCP** в [add.go](internal/cli/add.go):
меню и функции создания перечисляют конкретные виды через `switch`.
Для нового вида нужно добавить пункт меню и ветку создания.
Это небольшая явная правка в одном слое. Реестр фабрик усложнил бы текущие шесть видов.
Отчёты, приёмка и правило новичков от конкретного вида не зависят.

У `Park` нет отдельного интерфейса: сейчас нужна одна реализация учёта.
Для тестов техосмотра достаточно `ServiceCenter`, а для консоли —
стандартных `io.Reader` и `io.Writer`.

## Что произойдёт при расширении

| Расширение | Что потребуется и что сохранится |
|------------|----------------------------------|
| Новый транспорт, например электротрицикл | Реализовать `Transport`, а при потреблении энергии ещё `EnergyConsumer`. Добавить создание в консоль. `Park`, техосмотр по исправности и отчёты продолжат работать. |
| Сотрудник | Создать отдельный тип без `Inventory`. Сотрудник не попадёт на баланс. Для кадрового учёта понадобится отдельная задача и ADR. |
| Склад запчастей | Если учитывается сам склад как объект, реализовать `Inventory` и добавить его через `AddItem`. Он попадёт в количество вещей. Учёт остатков внутри склада потребует отдельных правил. |
| Другая политика техосмотра | Реализовать `ServiceCenter` и передать его в `NewPark`. Приёмка и консоль не меняются. |

Новые реализации должны соблюдать контракты интерфейсов. Передавайте ненулевые
значения и не меняйте их свойства после приёмки. Готовые типы домена возвращаются
из конструкторов значениями и не имеют методов изменения.

## Тесты поведения

Тесты находятся во внешних пакетах `domain_test` и `cli_test`.
Используются таблицы случаев, `t.Parallel()` и секции Arrange, Act, Assert.

- [TestAddTransportInspection](internal/domain/park_test.go) фиксирует решение сервиса.
  Мок принимает неисправный транспорт и отклоняет исправный.
  Это доказывает, что парк следует зависимости. `.Once()` проверяет число вызовов.
- `TestBasicServiceCenter` фиксирует реальную политику: принимать только исправный транспорт.
- `TestRejectionDoesNotReserveNumber` проверяет повторную приёмку после отказа.
- `TestDuplicateNumbers` проверяет единые номера вещей и транспорта и отсутствие лишнего техосмотра.
- `TestInvalidAdmission` запрещает нулевые объекты и обход техосмотра через `AddItem`.
- `TestBeginners` проверяет значения 1, 5, 6 и 10, исключение отклонённого транспорта и вещей.
- `TestParkReport` проверяет количество всех шести видов, общую энергию и копирование списка.
- `TestNewTransportType` проверяет расширение новым видом без правок парка и проверку контрактов интерфейсов.
- [Тесты конструкторов](internal/domain/assets_test.go) проверяют поля, диапазоны и специальные значения `float64`.
- [Тесты консоли](internal/cli/cli_test.go) проверяют команды, ошибки, восстановление диалога,
  полный сценарий `make demo`, конец ввода и ошибки потоков.

Мок генерируется из `ServiceCenter` командой `make mocks` по [.mockery.yml](.mockery.yml).
Он передаётся через тот же конструктор, что и настоящий сервис:

```go
service := NewMockServiceCenter(t)
service.EXPECT().Inspect(transport).Return(false).Once()
park, err := domain.NewPark(service)
```

Покрытие измеряется командой `make cover`. Ориентир задания — не менее 60%.
Результат проверки 2026-10-26: 97.2% суммарно, домен и консоль — по 100%.
Точка входа проверяется запуском `make demo`, правила и консоль — юнит-тестами.

## Порядок работы и сдача

Спецификация → ADR → код → `make check`. Правила работы агента находятся
в [AGENTS.md](AGENTS.md), журнал обращений — в [AI_USAGE.md](AI_USAGE.md).
Навыки шаблона сохранены в `skills/` и `skills-internal/`.

Вся работа идёт в `dev`. Для сдачи откройте MR `dev → master` со ссылками
на спецификацию и три действующих ADR. Спецификация и ADR должны быть
закоммичены раньше реализации. Не мержите в `master` до одобрения проверяющего.
Перед сдачей выполните `make check` и заполните личные сведения и рефлексию в журнале ИИ.
