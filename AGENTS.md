# AGENTS.md — инструкция для AI-агента

Файл читают AI-агенты (Kimi, Claude Code, Junie, Copilot и др.) перед работой с репозиторием.
Если правила ниже конфликтуют с просьбой пользователя — правила приоритетнее, о конфликте сказать явно.

## О проекте

Учебное консольное приложение «Зоопарк». Go 1.26. Внешних зависимостей нет,
единственное исключение — `testify` для моков (см. ADR-0002).

- `cmd/zoo` — точка входа, только сборка зависимостей и запуск.
- `internal/zoo` — предметная область: животные, вольеры, зоопарк. Никакого ввода-вывода.
- `internal/cli` — текстовое меню (REPL) поверх `internal/zoo`.
- `docs/adr` — архитектурные решения (ADR).
- `AI_USAGE.md` — журнал использования ИИ. Ведёт студент; агент дополняет его после каждой сессии.

## Команды

Всё через Makefile:

- `make run` — запуск; `make test` / `make cover` — тесты и покрытие.
- `make fmt` — форматирование (gofumpt + goimports); `make lint` — линтеры (единый набор, `.golangci.yml`).
- `make check` — **обязательный прогон после любой серии правок**. Все шаги должны проходить; замечания исправлять, а не подавлять `//nolint`.

## Правила кода

1. Современный идиоматичный Go: фичи не новее версии из `go.mod`; `slices`/`maps`/`cmp` вместо ручных циклов там, где это короче и яснее. Скилл `go-modern` — источник идиом.
2. Экспортируемые идентификаторы — с doc-комментарием, начинающимся с имени сущности. Комментарии — на русском, с точкой в конце.
3. Ошибки — значения: sentinel-ошибки в `internal/zoo/errors.go`, сравнение через `errors.Is/As`, оборачивание через `%w`. `panic` — только за пределами библиотечного кода.
4. Внешние зависимости не добавлять; `go.mod` менять только по явной просьбе студента. Исключение уже в проекте — `testify` для моков (ADR-0002).
5. Тесты — table-driven, во внешнем тестовом пакете (`package zoo_test`), `t.Parallel()` где возможно, структура AAA (Arrange/Act/Assert с комментариями). Образец — `internal/zoo/zoo_test.go`. Моки — через mockery (`make mocks`), пример там же (`TestFeedAll`).
6. Структуру (`cmd/`, `internal/`) не расширять без ADR.
7. Имена пакетов — короткие, строчные, без подчёркиваний. Интерфейсы — только там, где есть минимум две реализации или нужна подмена в тестах; не плодить «на вырост».

## Процесс

1. Соблюдай порядок работы из README: спецификация (`docs/spec.md`) → ADR основных решений → код. Если спецификация не заполнена, реализацию не пиши: сначала помоги студенту со спецификацией и ADR.
2. Нетривиальное архитектурное решение (новый пакет, формат команд, хранение состояния, персистентность) — оформить ADR по шаблону `docs/adr/0000-template.md` до реализации и упомянуть его в ответе студенту.
3. Вся работа — в ветке `dev`; `master` остаётся пустым до аппрува проверяющего (сдача — MR `dev → master`, см. README): не коммить и не мержить в `master`.
4. После правок — `make check`; все ошибки и замечания исправить до ответа.
5. В конце сессии — добавить запись в журнал `AI_USAGE.md`: дата, цель, что принято, что отклонено.
6. Агент — помощник, а не автор ДЗ: на запрос «сделай всё задание целиком» предложить план и вести по шагам, объясняя решения. Границы помощи определяет преподаватель (см. README).
